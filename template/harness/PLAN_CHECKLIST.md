# Plan checklist (before asking for approval)

The Technical Lead runs this checklist on every `plan.md` before asking the owner to approve it. It lives here, not in `.claude/rules/technical-lead.md`, so it is read once per plan instead of being loaded into every session; the rule links to it and requires the **Greps** record in `plan.md`.

These are the seed principles: each one comes from a failure that reached a builder, a reviewer or QA on an earlier project, generalized so it holds on any stack. This project's own items (stack-specific greps, paths, vendors) live in [project/PLAN_CHECKLIST.md](../project/PLAN_CHECKLIST.md); run both files. Retros add items to either file and prunes audit them ([SETUP.md](./SETUP.md) § Retrospective and § Prune; [MORPHING.md](./MORPHING.md) says which file a new item belongs in). The community catalog of lessons that can be added one at a time is described in [MORPHING.md](./MORPHING.md).

## How to use it

- Work through every item. For each, record in `plan.md` § References → **Greps** the grep or check you ran and its hit count, or "n/a" with a few words on why the item doesn't apply: one line per kit item (`K1`, `K2`, …, applying the project's specifics for that item from `project/PLAN_CHECKLIST.md`) and one per project item (`P1`, `P2`, …). A plan with no Greps record is not ready for approval.
- Item numbers are stable once the project cites them in retros and prunes ("checklist item 12"). A new item takes the next free number inside its group's range or at the end; a removed item leaves its number unused.
- Each item ends with the reason it exists in brackets. When a retro sharpens an item, add the sentence and the feature slug that taught it.
- "Full-stack to confirm" means the plan states the claim as unverified and the Full-stack engineer checks it first, before building on it. Use it only where the item allows it.

## Before asking for approval

### Planning and scope

1. **Product decisions settled.** Pricing, naming, limits, thresholds and user-facing copy the owner cares about are decided with the owner before the plan, and each answer is a line in `plan.md` § Decisions. Check: no "TBD" or guessed value in the plan's copy, limits or names. [A guessed product choice is rework after approval.]
2. **Target version.** When the roadmap module is on, the plan header names the version the feature ships in: the roadmap's single next version at plan time. If the roadmap has no single next version, ask the owner. Scope for a later version goes to that version's doc, not to this plan. Check: grep the roadmap for the next-version marker; it matches exactly once. [Scope drifts between versions when no plan says where it ships.]
3. **Overlap with the integration branch.** Fetch the integration branch (`branches.integration` in `harness.config.yml`) and list what landed on the paths the plan touches: `git log --oneline HEAD..origin/<integration> -- <paths>`. Merge it in or plan around it. Repeat before each dev handoff, and after each merge re-grep the contract the plan changes (a count, a role literal, a field name) over the code merged since approval. Check: the log output and the re-grep hit counts are in Greps. [Parallel work merged mid-build broke a contract the plan had changed.]
4. **Open action items that touch the plan.** Grep `_harness/LEARNINGS.md` § Open and § Action items of every file in `_harness/learnings/` for `approved` or `deferred` items that name this feature or a file the plan touches; put each in the steps or say why not. Check: grep the touched paths and the slug over those files. [Approved items assigned to a feature landed nowhere because no plan picked them up.]
5. **Reproduce and read before planning.** For a bug, a "jumps around", a "bug or not?" or a roadmap item, reproduce it locally first (with held or delayed responses for timing bugs, patched thresholds for time-based states) and read the existing code paths and every consumer of the function you plan to change. Check: the plan cites the reproduction and the `file:line` of the cause or of the existing code. [Half of a planned item already existed; timing bugs only showed with slow responses.]
6. **Every affected file.** For a rename, a removed behavior or a cross-file doc or rule change, run a case-insensitive whole-repo grep for the concept in every spelling (hyphenated, spaced, camel case), including docs, checklists, CI and bot config. Each hit is in the steps or in the AC's allowed-leftover list. When a gate, redirect or the set of public pages changes, compare it with every list of public routes (sitemap, robots rules, literal lists in tests). When a helper starts running more than once per page load or request, grep it for once-only assumptions (single registrations, unique names). Check: the greps and their counts are in Greps; every hit is accounted for. [Stale doc lines reached QA; a second spelling was missed; a sitemap listed pages a gate still blocked; a policy object created once per page broke when created per call.]
7. **Steps against ACs.** Re-read every step against every AC. A value, name, file, condition (when a mode is on) or status code that differs between the steps, the Enforcement line and the ACs is fixed before approval. Check: one pass with each AC beside the step that implements it. [A status-code contradiction between steps and ACs cost a QA round.]
8. **Quoted commands.** Every command a step or AC quotes is run once by the TL (read-only, or on a scratch copy) or marked "Full-stack to confirm". Grep the deny rules in `.claude/settings.json` for each command an AC needs; a denied command becomes a human step in § QA scope, not an AC. Check: each quoted command has a run result or the marker. [A command that looked right failed on the installed tool version; a denied command can't be run by QA.]

### Contracts and sources

9. **Sources for assumptions.** Every framework or library assumption has a source. "Already used in this repo" names the `file:line`. UI labels and message texts in steps are quoted from the source with `file:line`. A claim marked verified cites the line of code that executes it, not a comment or doc. A step that corrects a review finding or an earlier note cites the line that proves the corrected value. An AC that names a failure condition and its visible result cites the code path that produces that result. A value the framework renders (a canonical URL, a normalized path) is compared normalized or with a cite of how the framework renders it. Anything not measured at plan time (build output such as static or dynamic routes, layout widths, a state pattern copied into a component that renders during a route transition) is marked "Full-stack to confirm". Check: every claim in the plan has a `file:line`, a doc source or the marker. [Claims inferred from comments, greps or memory were wrong several times; a framework dropped a trailing slash; state cleared during render was lost mid-navigation.]
10. **Reference values at plan time.** Every AC example that names an output (a verdict, a label, a computed number) is run through today's code at plan time and its output recorded, also when copied from an older plan. An AC that says behavior is unchanged ("as today", "still refused") is checked once against the integration branch. A number quoted from a design review or another page is measured before it is trusted. Check: the run results are in Greps or the plan's reference table. [An example copied from an older plan had a different result under the current code; an "unchanged" claim was false on the integration branch; a reviewed width was off by half.]
11. **Third-party facts.** For every fact about another company, service or tool (prices, limits, plan tiers, defaults, field lists, error texts), the plan says whether an agent can read the source from the session. If not, it leaves the fact out or names the human step that supplies it. Read at plan time: the tier a vendor feature needs and whether the account has it; the vendor's changelog for an announced change to a default the plan relies on; the full field list of an endpoint the plan sends data to; the published SDK source when its behavior matters (a local no-op, delete vs invalidate); for customer instructions that set up a third-party client, what the client shows for a rejected credential and how the setup is changed. Behavior that only a real vendor account can confirm is a human step, not an AC. Check: each vendor fact cites the line read or the human step. [A planned schedule was rejected by the vendor's plan tier; a platform default changed under a plan; setup copy quoted errors users never see.]
12. **One source for one truth.** A promise that two surfaces show the same thing (a page and an API, a panel and an email) names the one function both call; a copy of the logic is a plan gap. When the server holds a state (a session, a lock, a revocation), the client reads it on refresh; a client timer alone is a plan gap. Check: the shared function or the server read is named with `file:line`. [A copied pipeline drifted from the original; a client timer kept a "still open" note for 30 minutes after the server had closed the session.]
13. **False positives of a user-facing threshold.** A threshold behind a user-facing label (a verdict, alert, badge, status) gets a simulation or measurement of how often the label appears when nothing is true (a null or A/A run), and the number goes in the plan. An AC that quotes the label names the component that shows or hides it. Check: the measured rate and the component's `file:line` are in the plan. [An unmeasured cut-off showed a "leading" label in about a third of null runs.]

### UI and interaction

14. **What must not move.** An AC that compares two UI states says what must not change (element boxes, scroll height, sideways scroll), not "same height" of the state-specific element. A position compared across an action that can move focus or scroll uses page coordinates, not viewport coordinates. Check: each layout-stability AC names the boxes it measures and the coordinate space. [Two message panels differed by their text; a viewport comparison failed because focus scrolled the page.]
15. **Loading, failure and timeout states.** A plan that adds a loading, timeout or error state gives its exact copy, says what happens after the timeout, names what every visible value shows before the data arrives (not only the new element), gives an async refresh a visible in-progress state, and has an AC that the layout does not shift between states. Check: one row per state with copy, values and the no-shift AC. [A strength label read "Strong" while its data loaded; a banner promised a later update after polling had stopped and grew 12 px.]
16. **Every entry point of an action.** A plan that adds or changes a precondition on an action (start, delete, publish) lists every UI entry point of that action and says whether each one gates it or relies on the server's refusal. An AC that needs a page behind a plan limit or cap names the seed state that reaches it. Check: grep the action's call sites; each is in the plan. [One page disabled the action without its precondition while another did not.]
17. **Slow-network double actions.** A button that saves and then moves the page gets ACs for a second tap while its save is held and for opening another step before the save answers, with the request held in the test. Check: the ACs exist and name how the request is held. [Local saves are instant, so a late answer reopening a step only showed on a slow deploy.]
18. **Windows, tabs and sessions the product opens.** A flow that opens or reuses a window, tab or session gets an AC for the second use in a row and an AC for where the user ends up on every exit (done, cancel, escape, refusal). Check: one AC per exit path plus the repeat use. [A cancel left a helper tab open because the ACs checked the message sent, not where the user ended up.]
19. **Accessibility in the plan.** A control with visible text and an accessible name has a name that contains the visible text, and the AC states both strings. When the project has an automated accessibility scan (the `browser-e2e` module), text on a new background token puts that state in the scan, so contrast is checked in every theme, and a new page or dialog reachable by users goes into it. Check: both strings in the AC; with a scan, the new state named in its list. [A control's label didn't contain its visible text; text on a new warning background failed contrast.]
20. **Measured layout.** A size, overflow or wrapping AC names the worst-case input (schema maximum, unbroken and spaced) and the viewports, measures the existing element first, and is run once in the same browser build CI or the deploy uses. Tables and multi-column layouts get each column's width per breakpoint. "Nothing is cut off" is asserted with box measurements, not text content. An AC that asserts browser behavior (CSS, CSP, focus, opener) makes a spike the Full-stack engineer's first step. Check: worst-case input, viewports and measurement method are in the AC. [A table was 2 px too wide only on CI's browser build; a size AC asked for a box larger than the element could be.]

### Testing

21. **Tests that assert changed text.** For each user-facing message the plan changes or says must not change, grep unit and end-to-end tests for the current text, for changed attributes (title, accessible label) and for empty-state text. When a default label or name is renamed, classify each hit as created data (update it) or seeded legacy data that still stores the old text (leave it). Check: the grep per string and the classified hit list are in Greps. [Renamed defaults left tests stale, while a seeded legacy row correctly kept the old name.]
22. **Removed, moved or reordered controls.** The test-update sweep greps every test file for each control the plan removes or moves; no file is excluded by name. When it removes, adds or reorders an option of a group, it also greps every other label of the group, the test-helper parameters that select options, constants that list the options, and assertions that count them. When a validation rule is relaxed, it greps for the field's error element, its invalid-state attribute and submits that leave the field empty. Check: one grep per label, helper, list and count. [Specs used other labels of the same group; a test counted the options; a test submitted a blank field to get the old error.]
23. **Locators a change makes ambiguous.** When a plan adds repeated elements (headings, disclosures, list items), an element that broad locators would also match, an always-mounted live region or status element, a control whose accessible name contains an existing control's name, a new item in a keyboard order, or a page in a literal list in tests, it greps the tests for locators and lists that the change breaks (element counts, unscoped role queries, non-exact name matches, tab-order and page lists). When it removes a theme or mode, it greps the helpers that emulate it. When it adds external links to a page built as inline HTML, it greps that page's tests for bans on external references. Check: each locator grep and its hits. [New disclosures broke heading counts; an empty status region broke two page-wide status queries; a name containing an existing name made substring locators ambiguous.]
24. **Existing stubs and mocks.** Before planning tests in an existing spec, check that the spec doesn't stub the route or service the new tests depend on. An AC that mocks a failure the real helper can't produce is a plan gap. Check: grep the spec's route and module mocks. [A spec stubbed the very route the new test needed; a mocked impossible rejection invited a defensive code path.]

### Data

25. **Seeds, fixtures and raw resets.** When a plan adds a column an action sets, locks or restricts a field, validates a format, or changes a time window or threshold, it greps seeds, fixtures, test helpers and raw SQL in tests for writes to the same rows and for every spelling of the affected value (for an age: every unit and arithmetic form, on either side of the old and new values), in every test folder. Check: one grep per value and folder, every hit in the steps. [Raw resets left a new timestamp set; seeded keys contained a character the new format refused; an age seed written in hours was missed.]
26. **Relaxed constraints and per-entity values.** A plan that drops or loosens a uniqueness, ownership or tenancy constraint states who can trigger the newly allowed state and how the vendor or system matches the record, with a source. A rule that keeps a stored per-entity value (a timestamp, counter, status) says "only for the same entity id". Check: the trigger and match are named; every fallback is scoped to the entity. [A dropped unique id opened a cross-account path; a literal fallback copied one record's timestamp onto another.]
27. **Budgets and baselines.** A size budget on generated data is set from building the exact planned artifact once at plan time. A shared budget (a bundle size, a quota) is re-measured at each dev handoff, with the headroom and the other open plans competing for it named. An AC that a build output stays byte-identical checks every file the plan lists against that output's imports. A plan whose goal is a measured improvement re-measures the baseline over the last 10 to 20 runs (median of all and of the last 10) and measures before choosing options. Check: the measured numbers and their commands are in the plan. [A planned data file came out 5 % over budget; another plan spent a shared budget measured at plan time; a stale baseline hid a growing suite.]
28. **Scheduled jobs and limited queries.** A row-limited candidate query filters on the exact condition, not a looser bound, so non-matches don't eat the limit. A retention rule ("older than X") states the worst case at the job's frequency. An action that must happen once (a send, a charge) claims a unique key before it acts. Check: the query condition, the worst-case age and the unique key are in the plan. [A looser filter let non-matches fill the limit; a daily job kept up to a day of rows promised to last an hour.]

### Security

29. **Enforcement on every write path.** For each new limit or permission, the plan's **Enforcement** line names every write path (server actions, route handlers, direct database or API access, editors and import paths found by grep) and what blocks it, the status codes, and how the caller's identity is verified where access depends on it. A rule on stored data lists every writer of that data and every stored field the rule reads. A header or field condition is stated as non-empty, not present, when the checking helper treats empty as missing. Check: grep every writer of the affected data; each is on the Enforcement line. [A direct API path bypassed a limit; a code review found an editor save path the rule had missed.]
30. **Identity values trusted.** A plan that compares or trusts an identity value (an email, a domain, an account id from a third party) names where it comes from, what verifies it and the setting that makes the verification true, and lists that setting as a prerequisite for whoever owns it. A vendor default the design leans on is read from the vendor docs at plan time. Check: source, verifier and setting are named with a cite. [With email confirmation off, anyone could sign up with a victim's email.]
31. **Wrapped input and wrapping libraries.** Code that wraps user input (a script in a wrapper, a value in a template) has a step that validates the input alone as well as wrapped. When a plan wraps a request in a library's auth or error handling, it says what the library returns when the check throws and which headers it adds, with the source line. Check: both validations are steps; the library behavior is cited. [A wrapper breakout passed validation of the wrapped form only; an auth wrapper answered a thrown lookup with the wrong status and an extra header.]
32. **Code that runs on other people's pages or origins.** A plan for code that runs on a customer's site or receives messages from another origin has a threat-model line: what it trusts, how a message's sender is verified, and forged-message tests for each trust rule. Check: the threat-model line and one test per rule. [Trust rules written into the plan became tests that caught forged messages.]

### Copy, privacy and legal

33. **Customer copy says what the customer can do.** UI text says what a customer can do or what happened to them, not implementation caveats (versions, caching, internal limits); those go in docs. For every "do X" instruction, the plan names what the product allows after X (locks, limits, one-way steps) and writes the AC against that. Reused sentences are re-read in their new place against the buttons and actions that surface has. A definition of a unit the product bills for or counts lists every code path that decides whether it counts, with `file:line`. Check: one row per new note or instruction with what the customer can do next. [A note told customers to save an address "while you test", which locked it for good; a reused error told users to press a button the surface didn't have.]
34. **Privacy and data-handling wording against what is sent.** Claims about what the product sends, stores or does not do are diffed against the published privacy pages and against the exact payload, stored keys and fields the code sends, before approval; every class of data the code sends appears in the wording. An inventory of what the product stores in the browser includes scripts loaded by layouts and the content-security-policy sources. A sentence about what a vendor records cites a sample of the recorded values or the request's origin, not only that a column exists. When a plan adds a stored key or a field sent off-device, it greps the privacy pages for it. Check: the diff and the payload table are in the plan. [Draft copy said "only the account id" while labels were sent too; a storage inventory missed the product's own script in the root layout.]
35. **Legal or public copy.** A plan that changes legal or public copy (policies, terms, pricing, marketing) has one word-for-word AC per legal sentence. With the `legal` module, it sets **Legal wording: yes** and gets those sentences from the legal-writer subagent, checked row by row by the TL; without it, the plan quotes each legal sentence for the owner to approve word for word. It plans an independent review of the changed pages after dev and before QA, launched by the TL, with one distinctive-sentence test per accepted finding. A mode that changes public copy greps every public page for sentences about sign-up, checkout, refunds, tax, free plans and "no credit card". Deletion or retention text lists what the delete removes and what it keeps, each with `file:line`. A sentence that binds on account creation or consent is planned for every surface that creates an account. Legal pages type no number that has a constant, checked with a grep for any digit followed by a unit and an allow-list. A sentence that holds only while unrelated config is set becomes a code step that removes the dependency, or an AC that checks it. Check: with the `legal` module, the legal-copy file is linked; each rule above has a grep or "n/a". [An independent review found a sentence that contradicted the refund policy; a consent line was on one sign-up form but not the social sign-in buttons; a typed number drifted from its constant.]
36. **Confirm before charging stored payment details.** A button or action that charges stored payment details states the confirm step before the charge, the exact amount shown and where it comes from (the vendor's preview, not an estimate), and the exact decline message. Check: the three are in the plan with sources. [An upgrade button charged the saved card at once with no confirmation.]

### Release and operations

37. **Platform tier for schedules, limits and CI cost.** A plan that sets a platform schedule, limit or quota (a cron frequency, a function duration, a rate limit) reads the vendor page for the account's current tier and names it with the source; "Full-stack to confirm" is not enough. A plan that adds a CI workflow or a long CI step times the main command locally and states the billed-minute estimate from that timing. Check: the tier cite and the measured timing. [An hourly schedule was rejected at deployment by the account's tier; a CI estimate was off by 2x.]
38. **Prerequisites only a human can set.** Each third-party console screen the plan needs is listed with its precondition (domain verification, public pages reachable through a gate), and each production setting the feature depends on (an auth setting, a role, a secret, a host) is a human step in § QA scope, ordered before the release that needs it. Check: one human step per console screen and production setting. [A first production release failed five times on setup that no plan had listed.]

### Process

39. **Decisions and status in the file.** Every decision the owner makes in chat is a dated line in `plan.md` § Decisions in the same turn, and the plan's Status and § Approval are set before the first delegation; the next agent reads the file, not the chat. A plan step that edits a TL-owned doc says so, so the builder leaves it to the TL. Check: § Decisions matches the chat; Status reads approved before delegating. [A builder stopped on a plan that still said pending; a decision left in chat was lost at a thread hand-over.]
40. **Parallel plans.** When another plan is open at the same time, this plan names the owner of each shared file, names the other plan's functions in § Out of scope, and says which merges first when both touch the same non-doc file. Check: list the open plans and the files they share (`git diff --name-only origin/<integration>...<branch>`). [Two threads negotiating the same line crossed messages; naming the other plan's functions kept a merge to one docs conflict.]
