# Harness modes

## Working alone (plain changes)

When `bash scripts/risk-check.sh` prints `Mode: plain`, the main chat makes the change itself: no Full-stack or QA subagent. That is light mode and small mode below. Full-stack and QA run only in full and bug mode (learned: on everyday changes the hand-offs between agents cost more than the work, and the risk check already sends risky ones to full mode). A bug fix off the risk paths is small mode too (§ Small mode, § Fixing a bug).

Working alone, the main chat follows the builder's rules as well as its own:

- Before the first edit, read `harness/agents/fullstack-engineer.md` § Do, § UI screenshots and § Before handoff, and `project/agents/fullstack-engineer.md` (this project's builder rules). Read `.claude/rules/testing.md` for the tests to write. Where those sections say `progress.md`, write the PR record (light mode), the plan's § Check (small mode) or the fix commit's record (a small-mode bug fix); § Ownership limits and § Hand back are for the subagent.
- With **UI change: yes**, also follow `harness/agents/qa-engineer.md` on screenshots and the layout pass (open each after-shot; check every page at the narrowest width when styles or a shared component change). With **Needs live app/services**, its rules for the local stack and `deferred: local` apply, and `project/CONTROLS.md` § Manual smoke when it has rows.
- Same branch, commit and PR rules as any feature (`AGENTS.md` § Golden rules, `harness/TECHNICAL_LEAD.md` § Commits and branches), and the same guard hook: a deny is final.
- The `before_qa` checks after the change, scoped by what changed (`end-of-task hook` for the `checks.on_stop` checks, which run when the turn ends: [CONTROLS.md](./CONTROLS.md) § End-of-task checks); then, for small mode, the `before_signoff` checks once in full on the final commit ([CONTROLS.md](./CONTROLS.md)). A check the environment refused is **not run**, never a pass.
- Before the hand-off, run `bash scripts/risk-check.sh` again with no files (§ Choosing mode, step 4). When it prints `Mode: full`, stop: write a full plan with this change linked, and the agents take it from there. For a bug fix that is a bug plan (§ Bug mode): the failing-test commit already made is the reproduction, so QA's reproduction run checks that the test fails at that commit for the reported reason instead of writing another.

## Full harness

**Use when** `bash scripts/risk-check.sh` prints `Mode: full` for the change (it touches a risk path in `project/CONTROLS.md` § Risk paths, deletes stored data, or changes more files than `mode.plain_max_files`), when the Technical Lead raises a plain change to full because the request leaves a real product choice open, or when the owner asks for full mode (§ Choosing mode).

**Process**

1. Create the feature folder under `_harness/features/<slug>/<version>/`.
2. Technical Lead → Full-stack engineer → QA engineer per [STRATEGY.md](./STRATEGY.md) and [SETUP.md](./SETUP.md). QA is lean: the Technical Lead hands it the plan, the diff and the check results, and it reviews the diff and makes one pass over the criteria, at `medium` unless Full-stack is `xhigh` ([agents/qa-engineer.md](./agents/qa-engineer.md) § Lean QA). On a risk path, or at `xhigh`, the Technical Lead's code review runs between them ([SETUP.md](./SETUP.md) § Code review before QA).
3. Run the checks from [CONTROLS.md](./CONTROLS.md) before each handoff.
4. The learnings file at the end, with the retro inside it ([SETUP.md](./SETUP.md) § Retrospective).

## Light mode

**Use when** the risk check prints `Mode: plain` and the change alters no behaviour: documentation, comments, formatting, config that changes nothing at run time, a dependency bump whose named checks pass, or an approved prune or small retro item applied to harness docs. A change a user can see (copy, layout) or that changes what the code does is small mode or higher, however small.

**Process**

- The main chat makes the change itself (§ Working alone), application code included. The owner's request is the approval; there is no plan to approve.
- No `_harness/` feature folder required, no QA agent, no retro: the named checks are the only verification.
- When the change turns out to alter behaviour or to need a test of its own, stop before going further: it is small mode, with a plan the human approves.
- Still run the applicable named checks if the change touches code ([CONTROLS.md](./CONTROLS.md)): the `before_qa` checks, scoped by what changed. The record is the PR (or the commit message with no PR): the checks run with their exit codes (`end-of-task hook` for the `checks.on_stop` checks), under a **Light mode** line saying why the change qualified.
- With `cost.track` on, the closing message ends with the `Cost ≈ $…` line from `bash scripts/feature-cost.sh` (with `--since <time the task started>` when the session did other work first). It goes in the message only; light mode writes no file for it.

## Small mode

**Use it when** the risk check prints `Mode: plain` for the files the change will touch and the change alters behaviour (a flag, a field, a format, a message, a sort order, a limit, pagination). The script, not a reading of the request, decides: a change to a risk path is full mode however small, and a change off them is small mode however it is worded. A bug fix off the risk paths is small mode with the steps in § Fixing a bug, and no plan file; on a risk path it is bug mode. A new migration that only adds is small mode with the steps in § Additive migration.

**Process**

The main chat plans, builds and checks the change itself (§ Working alone); the plan and the merge gate stay (learned: on small, fully specified changes, full mode cost many times a plain session for the same result).

1. **Plan.** Read the code the change touches, then write `_harness/features/<slug>/<version>/Plan/plan.md` from [templates/small-plan.md](./templates/small-plan.md): the risk check's output, the change, the files, 3 to 8 acceptance criteria with their tests, and the limit. No plan checklist run. The human approves it as any plan.
2. **Build.** Make the change and write the tests the criteria name, then run the `before_qa` checks. A change that needs more than § Limit allows stops before the change: write a full plan with this one linked.
3. **Check.** On the final commit, run the `before_signoff` checks in full and fill the plan's § Check: each check with its exit code (`end-of-task hook` for the `checks.on_stop` checks, which run when the turn ends: [CONTROLS.md](./CONTROLS.md) § End-of-task checks), and each criterion with the test or output that shows it holds. A criterion nothing shows is not met: fix it or stop and tell the human. No `progress.md` or `qa-result.md`.
4. **Close.** § After QA pass as in full mode, with § Check in place of the QA verdict. The learnings file is the look-back, as in full mode: the verdict and cost lines, and § What went wrong with its action items only when something did. It counts toward the prune counter, so the prune sees whether small mode lets problems through.

### Additive migration

When the risk check prints `Mode: plain` with a `+ <file>: additive migration` or `+ <file>: database test` line, the change runs in small mode with two more steps (learned: a migration that only added a column sent a whole feature to full mode, the agents' runs cost more than the work, and the risk the script can't rule out is in the code that reads the new column, which a review covers):

- **Database tests.** The plan's § Acceptance criteria include the database tests: the new tables' row-level security lets the owner in and keeps everyone else out, and each new column or constraint holds. § Check records the project's database check (`project/CONTROLS.md`) with its exit code. With the `data-access` module, stage A runs too ([modules/data-access/](./modules/data-access/README.md)), its rows in § Check.
- **One code review.** Before the hand-off, run `/code-review medium` on the branch and fix or answer each finding; § Check lists them with what was done. When a finding is about who can read or change data, stop: it is full mode, with this plan linked.
- **The owner applies it.** No agent applies a migration to a shared environment; the steps file's **Apply to the integration environment** block names the migration files in order for the owner (`harness/SETUP.md` § After QA pass, step 4).

A `+` line always means small mode with a plan from [templates/small-plan.md](./templates/small-plan.md), even for a bug fix (not § Fixing a bug's commit record) or a change that alters no behaviour (not light mode).

The script reads the file against a short allow-list and calls it additive only when it is a new `.sql` file in a risk area named for the database, and every statement has one of these shapes, in the `public` schema: a new table (no `if not exists`, no copy of another table) with row-level security turned on; columns with plain-value defaults, checks, unique keys and foreign keys added to a table; indexes; policies for named roles (never `anon` or `public`, never a condition written as always true such as `true` or `1=1`; the code review reads the rest) and grants (never `with grant option`) on the new tables, and row-level security turned on for them; `stable` or `immutable` SQL functions whose body only selects and whose name no `.sql` file of the integration branch uses yet (a new overload can take over an existing call; the script can't see functions that live only in the database, so the code review checks the names against it); and comments. Expressions may call only plain value functions and the functions the file creates. Tables and columns named for sign-in, secrets, money or permissions stay full, and so does anything it can't read safely (a prefixed string, a backslash in a string, a `$` outside a `$$` body, a doubled quote in a name, another schema). A `.sql` file in a test folder, outside the migrations, counts as a database test. Anything else the change touches on a risk path, or the owner choosing full, makes the database files risk paths again. A migration it can't read yet (named but not written) is full with a note: write it first, then run the check again. When it still prints `Mode: full`, move the draft into the full plan as the proposed migration and delete the file, so Full-stack writes it.

### Fixing a bug

A bug fix whose files the risk check prints `Mode: plain` for runs as small mode, alone, with bug mode's order kept and no plan file. These steps replace § Small mode steps 1 to 4 (learned: a small fix off every risk path cost several times a plain session once Full-stack and QA took it, and still cost far more than one once the main chat wrote a plan, a check record and learnings for a fix it made alone).

- **No plan file.** The record is the commits and the PR (or the last commit's message with no PR), as in light mode. The owner's report is the approval only for restoring behaviour: what worked before (with the commit), or what an AC or the docs already promise. When **Should** has no such source, or the fix adds a flag, field, option, message or default nobody promised, it is not a bug fix: stop, it is small mode with a plan the human approves.
- **Failing test first.** Write the regression test with its **edge inputs**: the inputs next to the symptom that the fix must also get right, those that apply. They are equal values (two items with the same sort key or timestamp), none, one, exactly at a limit or page edge, and a last page that is not full. When the bug is in an order (a sort, paging, "the latest"), the order ends with a unique key such as the id, so items with equal values keep one order every time (learned: a paging fix sorted by a timestamp alone passed its test, yet items with equal timestamps could still move between pages). Run it and commit it alone as `WIP(<slug>): failing test`. Its message holds the risk check's output, **Symptom**, **Should** with its source, **Edge inputs** (each one in the test, or `n/a: <reason>`) and the failure's tail. Only the reported case must fail; its edge cases may pass. When it doesn't fail for the reported reason, stop and tell the human: nothing gets fixed blind.
- **No test can reach it** (a third-party console, a device, a live service only): bug mode, where QA records a manual reproduction ([templates/bug-plan.md](./templates/bug-plan.md) § Regression test).
- **Root cause, then the smallest fix.** Name the root cause in your reply before changing code: the `file:line`, why it happens, why no test caught it, and the same pattern elsewhere with the grep and its hit count. Then make the smallest fix that turns the test green, edge inputs included, without editing the test. A same-pattern hit is fixed in this branch only when the human says so; otherwise the record lists it as out of scope with the reason. A fix that needs a risk path stops: bug mode, reusing the failing-test commit (§ Choosing mode, step 4), with the root cause copied into the bug plan's § Code path read. That includes an adjacent defect: when an edge input the test names, or a defect next to the symptom in the same code path, can only be fixed by editing a risk path (for example the tie-breaker of an order that lives in a risk-path file), do not list it as out of scope and finish; it is bug mode for the whole fix (learned: a paging fix left the `id` tie-breaker undone because it sat in a risk-path file, so items with equal timestamps could still move between pages). The out-of-scope listing below is for the same pattern in other places, not for a defect the failing test's own edge inputs call for. A fix that needs new behaviour stops: small or full mode, with a plan the human approves.
- **Check:** the `before_qa` checks after the fix, then the `before_signoff` checks once in full on the final commit, and the risk check again with no files (§ Working alone).
- **Record** in the fix commit's message and the PR: **Commit**, the `git rev-parse HEAD` the `before_signoff` checks ran on (the merge gate checks it, [CONTROLS.md](./CONTROLS.md) § Merge gate); **Root cause**; **Escaped**, one line on why no test caught it; **Proof**, that the test failed at the failing-test commit, passes now and is unchanged since (`git diff <hash> HEAD -- <test file>` prints nothing), and the reproduction no longer shows the symptom; **Checks**, each with its exit code (`end-of-task hook` for the `checks.on_stop` checks, **not run** with the reason for any the environment refused, `deferred: local` for one that needs a live service); **Screenshots** for a UI change; and the hand-off risk check's first line. With `cost.track` on, the closing message ends with the `Cost ≈ $…` line, as in light mode.
- **Close:** a step only the human can do goes to a steps file as [SETUP.md](./SETUP.md) § After QA pass step 4 says; then push and mark the PR ready (step 5).
- **No learnings file** unless something went wrong or the harness should change: the test didn't fail for the reported reason, a check failed after the fix, the fix took more than one try, the hand-off risk check printed `Mode: full`, or the **Escaped** line points to a harness rule, checklist item or named check that would have caught the bug. Then write the learnings file as § Small mode step 4, with the **Escaped** line and its one action item (§ Bug mode step 6). A missing test in the project alone is fixed by the regression test and needs no file.
- **Not for a hotfix:** a production hotfix is bug mode whatever the risk check prints ([RELEASE.md](./RELEASE.md) § Hotfix).

## Bug mode

**Use when**

- Something that worked, or that an AC, the docs or the product promise, is broken: a bug report, an error in production, "this used to work", and the human wants it fixed, and `bash scripts/risk-check.sh` prints `Mode: full` for the files the fix will touch (off the risk paths it is small mode, § Fixing a bug)
- A production bug that can't wait for the next release: bug mode on a hotfix branch ([RELEASE.md](./RELEASE.md) § Hotfix), whatever the risk check prints

Not for wrong copy or a typo that nobody reported as broken (small or light mode, § Choosing mode), for new behaviour that fixes nothing (full), or for "why does this happen?" with no fix asked yet (research, then § Choosing mode step 2 if it is one).

**Process**

The three agents and the merge gate stay as in full mode; what changes is the order and the plan. The test that proves the bug comes before any fix, the cause is written down before the code changes, and the fix is the smallest one that makes the test pass.

1. **Plan (Technical Lead).** When production is broken right now, first tell the human whether a rollback ([RELEASE.md](./RELEASE.md) § Rollback, theirs to run) would stop the damage while the fix is made. Create the feature folder `_harness/features/<slug>/<version>/` and write `Plan/plan.md` from [templates/bug-plan.md](./templates/bug-plan.md) (it replaces the full plan): the symptom, where it was seen, what should happen and the source that says so, the reproduction steps, the code path the TL read itself, the regression test QA writes, the fix limit, and the branch (the integration branch, or a hotfix). Run the pre-approval checklist as in full mode: § Planning and scope always (item 5, reproduce and read, is the heart of a bug plan), other groups only when the fix area needs them, the rest as one "n/a" line per group. The human approves the plan, including the branch; a hotfix is never the TL's call alone.
2. **Reproduce (QA).** The Technical Lead launches QA with the bug-reproduction brief ([HANDOFFS.md](./HANDOFFS.md) § Subagent prompt blocks). QA writes the regression test the plan assigns, runs it, and records in `QA/qa-result.md` § Reproduction that it fails for the reported reason, with the failure's tail. It fixes nothing. The Technical Lead commits the test alone (`WIP(<slug>): failing test`), so the history shows it red before the fix. When QA can't reproduce it, it records what it tried; the Technical Lead takes that to the human (more detail, research mode, or close as not reproduced) and nothing gets fixed blind. This run is not a QA round.
3. **Root cause and fix (Full-stack).** The Technical Lead launches Full-stack with the bug-mode brief. Full-stack writes `Development/progress.md` § Root cause first (the `file:line`, why it happens, since when, why no test caught it, and the same pattern elsewhere with the grep and its hit count), then makes the smallest fix that turns the regression test green, edge inputs included, without editing the test, and runs the `before_qa` checks as usual. A fix that would cross the plan's **Fix limit** (new behaviour, a migration, a public API change, a risk area the plan doesn't name, files beyond the plan) stops before the change and hands back: the Technical Lead re-plans (a full plan, with the bug plan linked) and asks the human. The Technical Lead checks § Root cause against the code (`file:line`) before QA, like any subagent finding ([SETUP.md](./SETUP.md) § Findings from a review subagent), then runs the code review before QA on the fix's diff when the risk check named a risk path (a fix off them, a hotfix or one raised by file count, skips it; [SETUP.md](./SETUP.md) § Code review before QA).<!-- module:security --> With the `security` module, a fix that changes who can sign in or read or change data, moves money, handles secrets or deletes or shares people's data gets the security review before QA whatever the effort ([modules/security/](./modules/security/README.md) § Security review before QA).<!-- /module:security -->
4. **Re-run (QA).** The normal QA pass on the bug plan's ACs: the regression test, unchanged since the failing-test commit, now passes with its edge inputs; the reproduction steps no longer show the symptom; each same-pattern place is fixed or out of scope with a reason; and the `before_signoff` checks. QA rounds, rework and escalation are as in full mode. The failing-test commit is the negative run [testing.md](../.claude/rules/testing.md) asks for.
5. **After QA pass.** [SETUP.md](./SETUP.md) § After QA pass as in full mode: the steps file (for a hotfix, at least the check in production after the merge), the PR marked ready. On a hotfix branch, the rest is [RELEASE.md](./RELEASE.md) § Hotfix: the `Hotfix vX.Y.Z` title, the tag, and bringing the fix back into the integration branch.
6. **Retro (Technical Lead).** The learnings file `_harness/learnings/<slug>-v<version>.md` ([templates/learnings-entry.md](./templates/learnings-entry.md)) is the look-back: the verdict and cost lines, **Escaped** (which feature let the bug through, and the AC, check or review that should have caught it, from § Root cause), the escape as a line in § What went wrong, and one action item for it: the rule, checklist item or test that would have caught it, or one line on why none would; a rule it adds ends with `(from <slug>, <date>)` ([MORPHING.md](./MORPHING.md) § Rule provenance). An escape is the one miss QA never saw, so it is the retro's best source of rules (learned: a run of clean retros added no rules while a bug of the same kind sat on a new route). The fix also checks the sibling paths for the same gap (other routes or pages that read the same data) and closes them in the same branch. The Technical Lead decides items as in § Retrospective. It counts toward the prune counter like a feature, so the prune sees what keeps escaping. The hand-off message ends with the cost and prune counter lines.

## Research mode

**Use when**

- The human wants an answer, not a change: how something in the repo works, why a bug happens, which library or service fits, what a new API version changes, how others solve a problem
- A question has to be settled before a feature can be planned, and finding the answer means reading a lot of code or the web

**Process**

1. The Technical Lead creates `_harness/research/<YYYY-MM-DD>-<slug>.md` from [templates/research.md](./templates/research.md) and writes § Question, § Scope and § Context (with the current commit), and the researcher effort ([SETUP.md](./SETUP.md) § Effort per feature).
2. The Technical Lead launches the **researcher** subagent (Agent tool, the variant for that effort) with the file's absolute path. Two independent questions (for example one about the repo and one on the web) can go to two researchers at once, each with its own file.
3. The researcher, which has no shell or edit tools, replies with the findings, recommendation and sources; the Technical Lead pastes the reply's sections, unchanged, between the file's two lines.
4. The Technical Lead re-opens the sources behind the findings the recommendation depends on (§ Check), then records § Decision: a feature to plan (in full mode, with the research file linked from `plan.md` § References), a light-mode change, or no action. Decisions that change product behaviour, add a step for the human or cost money are the human's. With the decision it fills the three § How it went lines: whether the check held, whether the scope and researcher effort were right, and whether the answer got used, and the header's **Cost** line from `bash scripts/feature-cost.sh` (with `--since` when the session did other work first).
5. The research file is committed like a light-mode docs change, or on the feature branch when it leads to a plan. Files that end in `no action` are kept: they record what was checked.

No application code changes, no QA, no retro, and research files don't count toward the prune counter: a full retro would have little to look back on, and research doesn't change how features are built. § How it went is the look-back instead; the prune reads it across research files and proposes tweaks ([SETUP.md](./SETUP.md) § Prune).

**Research before a plan.** In full mode the code scout maps the code before every plan (harness/TECHNICAL_LEAD.md § Full mode, step by step); the Technical Lead may also launch the researcher before planning, for a question the map can't answer, such as an unfamiliar API or a choice between designs; the file then lives at `<feature>/<version>/Research/<topic>.md` and `plan.md` § References links it. It is optional: small features don't wait on it. The Technical Lead still reads the exact files and functions the plan changes itself, because the plan's detail is what prevents rework.

## Choosing mode (Technical Lead)

The first match wins. The human's wording ("quick fix", "ship it fast", "no time for QA") never changes the mode; only the owner choosing one does ("use full mode", "run it plain"), passed to the script as `--force full` or `--force plain`, or set for every change in `harness.config.yml` → `mode.force`.

1. **A question, no change asked** ("how does", "why does", "which should we use", "compare") → research mode. A question one or two files the Technical Lead reads anyway can answer gets a direct answer, with no research file.
2. **Something that worked is broken and a fix is asked** ("bug", "broken", "error in production", "this used to work"): read the code path, name the files the fix will touch and run `bash scripts/risk-check.sh <files>`. `Mode: full` → bug mode, and its Full-stack never runs at `medium`. `Mode: plain` → small mode with the bug steps (§ Fixing a bug); with a `+ <file>` line, small mode with a plan (§ Additive migration). A fix that can't wait for the next release is bug mode on a hotfix branch either way.
3. **Any other change:** name the files it will touch and run `bash scripts/risk-check.sh <files>`. `Mode: full` → full mode. `Mode: plain` → light mode when the change alters no behaviour (§ Light mode) and the script printed no `+ <file>` line, small mode otherwise (§ Additive migration). When the owner forced plain and the script still names a risk path, the change runs alone too, with no QA agent (§ Working alone): forcing plain is the owner's choice to go without the agents, so say so in the plan or the PR record. The Technical Lead may raise plain to full when the request leaves a real product choice open, naming the choice; it never lowers full to plain. The script's output goes in the small plan's § Why small, a bug fix's failing-test commit, or a light change's PR or commit record.
4. **Before the hand-off** of a small or light change, run `bash scripts/risk-check.sh` again with no files: it reads what the branch really changed. When it now prints `Mode: full`, stop and switch to full mode (a plan, with the first one linked, and QA) before anything is handed off; for a bug fix, bug mode, reusing the failing-test commit (§ Working alone).
