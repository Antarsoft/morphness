## What changed

- **QA starts from what the Technical Lead hands it.** The QA prompt block in `harness/HANDOFFS.md` now carries the merge base (in round 2, the commit round 1 tested), `git diff --stat <base>`, the untracked new files and `bash scripts/checks.sh status`, so QA doesn't search for what changed or rerun a check that already passed.
- **New `harness/agents/qa-engineer.md` § Lean QA.** QA reads the code through `git diff <base>` and the untracked files, and opens another file only where the diff, a criterion, a failing test or a checklist it already follows (the layout pass, data-access stage A) points. It tests each criterion once and runs each check once; a second round happens only after a fail.
- **QA runs at `medium` unless Full-stack is `xhigh`.** `harness.config.yml` → `agents.qa.default` is `medium`; `qa-engineer-medium` is the default agent and `qa-engineer` (high) is for `xhigh` plans. A risk path or a data-access feature no longer raises QA on its own: the risk path already puts the change in full mode and keeps Full-stack off `medium`, and stage A's checklist covers the database. `harness/SETUP.md` § Effort per feature, both plan templates and the data-access module say so, and the risk-area rule now reads "Full-stack is never `medium`" (`harness/TECHNICAL_LEAD.md`, `project/HARNESS_AGENTS.md` § Effort per feature, the `risk_areas` comment in `harness.config.yml`).

## Why

We expect most of QA's cost on a risky feature to come from reading the codebase to find the change and rerunning checks that had passed. Its job is a fixed list of criteria, so depth comes from the criteria, the checks and, at `xhigh`, the code review before QA, not from reading more.

## How to apply

1. In `harness.config.yml` → `agents.qa`, set `default: medium`, unless this project chose `high` on purpose (a prune that tuned it, or a note in `project/HARNESS_AGENTS.md` § Effort per feature); then leave it, and make sure `project/HARNESS_AGENTS.md` § Effort per feature has a bullet saying "QA defaults to `high`". In the `risk_areas` comment in `harness.config.yml`, say "never medium Full-stack effort".
2. In `.claude/agents/qa-engineer-medium.md`, change the description's last sentence to "Default (effort medium): use unless the plan's Agent effort says QA high."; in `.claude/agents/qa-engineer.md`, to "Effort high: use only when the plan's Agent effort says QA high (Full-stack xhigh)." In `project/HARNESS_AGENTS.md` § Agents, move `(default)` from `qa-engineer` to `qa-engineer-medium`. Skip this step if you left the default at `high` in step 1. Either way, in § Effort per feature, change "**Risk areas (never `medium`):**" to "**Risk areas (Full-stack never `medium`):**".
3. Merge `harness/agents/qa-engineer.md` (§ Lean QA and step 1 of § Before you start), the QA prompt block and flow step 2 in `harness/HANDOFFS.md`, `harness/MODES.md` § Full harness, `harness/SETUP.md` § Effort per feature, `harness/TECHNICAL_LEAD.md` (the Agent effort bullet), the **QA** line of `harness/templates/plan.md` and `harness/templates/bug-plan.md`, and, with the data-access module, its § Technical Lead.
4. Open plans keep the QA effort the owner approved.

## Skip if

Never: every project with full or bug mode runs QA. A project that keeps QA at `high` still takes step 3; its § Effort per feature bullet tells the Technical Lead to pick the `high` agent.
