## What changed

The Technical Lead opens a feature's PR as a **draft** the first time it pushes the feature branch,
marks it **ready** once QA passes on the final commit, and moves it back to draft if QA fails after
that. Release and hotfix PRs follow the same states. Merging stays the owner's. With the
`ci-cd` module, CI skips drafts unless the new `ci_cd.on_drafts` is `true`, runs when a PR is marked
ready, and also runs in a merge queue (`merge_group`).

## Why

Before, no PR existed until QA had passed and the owner asked, so CI first ran after QA had already
signed off, the merge-order check couldn't see feature branches that overlapped, and "mark a PR
ready" in the merge gate had no draft to come from. A merge queue that required CI would never
finish, because CI didn't listen for `merge_group`.

## How to apply

1. Merge the PR states into `.claude/rules/technical-lead.md` § Commits and branches (and the
   command-vocabulary rows), `harness/SETUP.md` § After QA pass step 5, and `harness/RELEASE.md`
   (the policy line under § Branches, release steps 2 and 3, hotfix step 2). Keep any PR rule the
   project added.
2. With the `ci-cd` module and a CI workflow the harness wrote: ask the owner whether CI should
   also run on drafts (suggest no for a private repo, yes for a public one) and add
   `on_drafts: true|false` to `ci_cd` with the template's comment. In the workflow add
   `ready_for_review` to the `pull_request` types, the `merge_group:` trigger, the job-level `if`
   with that value filled in, the `|| github.ref` concurrency fallback and the `merge_group` guard in
   the scope step. Merge the module README's two new rules and its merge-queue owner step.
3. A CI workflow the project brought itself: describe the same three changes to the owner and apply
   them only on a yes.
4. Any open feature PR stays as it is; the new states apply from the next feature.

## Skip if

Skip steps 2 and 3 when `pr_host` is `none` (there are no PRs) or the project has no CI.
